Problem Statement and Motivation

Many small utility offices and housing societies in India still handle electricity, water and gas billing on paper. A meter reader writes readings in a register, someone in the office types them into a spreadsheet, and the bill is worked out by hand from a tariff table. Going through sample bills and the way these offices usually work, the same problems kept coming up: slab rates get applied wrongly, a typo in a reading gives a huge (or negative) bill, payments can only be made at a counter, complaints get lost, and the manager has no quick way to see how much money is still due.

Problem statement: build a web application that keeps customers, connections, meters, readings, bills, payments, complaints and outages for all three utilities in one database, with separate views for the admin, employees and customers.

This topic was given to us for our DBMS project. Since it is a proper multi-user system with real business rules, we decided to build the same system for SEPM too. The DBMS side looks at the schema, triggers and views; this report is about how we engineered it, phase by phase.

Project Objectives

  1. Let employees enter meter readings in a form that shows the last reading and refuses impossible values.
  2. Generate the bill automatically from each reading using slab tariffs, a fixed charge and tax.
  3. Give customers a portal to see their bills and usage, pay online and raise complaints.
  4. Track complaints and outages, and tell affected customers automatically.
  5. Give the admin a dashboard with revenue, dues, complaints and consumption by area.
  6. Keep the data correct with database constraints and triggers, and keep each user to their own pages.
  7. Follow the Waterfall model properly, with a document at the end of each phase.

Process Model and Feasibility Study

Why Waterfall

We went with the Waterfall model. Our requirements were clear from the start (metering and slab billing follow fixed rules), the DBMS course needed the full database design before any coding, and the semester has fixed checkpoints that line up well with finishing phases. Most of us are also new to web development, so a clear order of steps was easier to follow than sprints. To reduce the usual Waterfall risk of finding mistakes late, we reviewed each phase's output as a team before moving on, and wrote tests while coding instead of leaving them all for the end.

System Design

Architecture

The system has three layers. The browser shows HTML pages, Flask route functions handle requests and run the business logic, and SQLite stores everything. Pages are built on the server with Jinja templates, so there is very little JavaScript; the only API call is the one that fetches the last meter reading for the reading form.

ModuleWhat it does
app.py, auth.pySets up the app, login/logout, and the check that each page is opened by the right role
db.pyOpens one database connection per request and closes it after
billing.pySlab bill calculation (a plain function we can unit test) and saving the bill
routes_staff.pyAll admin and employee pages
routes_customer.pyCustomer portal; every query is limited to the logged-in customer
schema.sql, seed.pyTables, triggers and views; demo data loader

Database design

The schema is in 3NF: repeating data such as readings, payments and slabs sits in its own tables, and tariff rates are stored once in tariff_plans / tariff_slabs instead of on each connection. The one place we broke this on purpose is bills, which keeps a copy of the units and charges at the time the bill was made. Tariffs change, but an issued bill should never change.

Trigger / viewRule it enforces
trg_reading_monotonic, trg_reading_date_orderA new reading can't be lower than the last one or dated before it
trg_no_overpayA payment can't be more than what is still owed
trg_payment_statusAfter a payment, mark the bill paid or partial and notify the customer
trg_bill_notify, trg_outage_notify, trg_complaint_statusSend notifications for new bills, outages in the customer's area and complaint updates
v_bill_summary, v_overdue_bills, v_monthly_consumptionReady-made joins used by the bill pages, overdue list and charts

Billing formula. For each slab: units in slab = max(0, min(U, upper limit) − lower limit). Energy charge = sum of units in slab × rate. Total = (energy + fixed) × (1 + tax%). For 250 kWh on the domestic plan: 100 × 3.50 + 150 × 5.00 = 1,100, plus 50 fixed = 1,150, plus 5% tax = ₹1,207.50.

Key implementation decisions

  • Rules live in the database. Readings going backwards and overpayments are blocked by triggers, so even a bug in a page can't save bad data. The page just shows the trigger's message.
  • Check readings twice. JavaScript warns the user instantly, and the trigger is the real guarantee.
  • Billing is a separate function, so we could test it against amounts we worked out by hand.
  • A reading and its bill are saved together in one transaction; if one fails, neither is kept.
  • Customers never pick an ID in the URL. Their pages always use the logged-in account, and opening someone else's bill gives a 403.
  • No secrets in the code. The secret key goes in a config.py that git ignores.

Challenges Faced and Solutions Attempted

  • Most of us hadn't built a web app before. We used Flask with plain HTML, built one page together, and copied that pattern for the rest.
  • Slab billing was easy to get wrong at the slab edges and with decimals. We wrote it as one small function and tested edge cases.
  • Readings going backwards if someone skips the form. We added triggers so the database itself refuses them.
  • Old bills changing after a tariff edit. We store a copy of the charges on each bill.
  • Charts mixing kWh, kL and gas units. Comparison charts use rupees; usage charts are drawn per utility.
  • Tests affecting each other. Each test now gets its own fresh database file.
