Software Process Model and Feasibility Study

Choice of process model: Waterfall

We follow the classical Waterfall model: each phase produces a document that is reviewed and frozen before the next phase starts. Waterfall suits this project because:

  • The requirements are well understood and stable: the domain, metering, slab billing and payments, follows published tariff rules and the scope was fixed by the course.
  • The DBMS course needs a complete database design up front (ER model, normalisation), which matches Waterfall's design-before-code approach.
  • The course has fixed milestones (mid-semester and end-semester), which map naturally onto phase completion.
  • The team is new to web development, so a clear, documented sequence of phases is easier to manage than iterative sprints.

Because pure Waterfall makes it costly to find mistakes late, we added two small safeguards: each phase ends with a team review against the previous phase's document, and unit tests were written alongside implementation instead of only at the end. The overall flow remains sequential.

Feasibility study

Technical feasibility

The system needs only a web server, a relational database and a browser. We use Python with the Flask framework and SQLite, which are free, run on any laptop (Windows, Linux or macOS) and need no separate database server. SQLite supports everything the DBMS part needs: primary/foreign keys, CHECK and UNIQUE constraints, triggers, views and indexes. Team members already know Python and SQL from earlier courses; Flask and HTML templates can be learned in a few days. Conclusion: technically feasible.

Economic feasibility (development cost)

For a real utility office, the main benefits are fewer billing errors, faster collection and less manual data entry, at negligible software cost. Conclusion: economically feasible.

Operational feasibility

The users are office staff, field meter readers and customers, all of whom already use smartphones and UPI apps. The interface uses simple forms, one page per task, with the same layout as common billing portals. Validation messages are shown in plain language (for example "Reading cannot be lower than the previous reading"). Little training is needed. Conclusion: operationally feasible.

Schedule feasibility

The semester has about 14 working weeks. The plan (section 12) gives roughly 4 weeks to feasibility, requirements and design, 6 weeks to implementation and 4 weeks to testing, deployment and documentation. Core features were finished by mid-semester, so the schedule is realistic. Conclusion: feasible within the semester.

Legal and ethical feasibility

Only sample (fictional) customer data is used. Passwords are stored as salted hashes, and customers can see only their own data. A production version would need to follow the Digital Personal Data Protection Act, 2023 (consent and data minimisation) and RBI/PCI rules for payment data; our simulated gateway stores no card or UPI details. Conclusion: feasible for an academic prototype.
