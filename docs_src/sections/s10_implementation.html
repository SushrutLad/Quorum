Important implementation decisions

  1. Business rules in the database, not only in Python. Monotonic readings, overpayment and status updates are triggers, so the rules hold even if a page has a bug or data is entered another way. The Python code catches the trigger error and shows its message to the user.
  2. Validation twice for readings. JavaScript gives instant feedback (good usability), and the trigger gives the real guarantee (JavaScript can be bypassed).
  3. Billing logic is a pure function (calculate_bill), separate from Flask and SQL, so it is easy to unit-test with hand-calculated examples.
  4. Bill snapshot. Charges are copied onto the bill at creation time so tariff edits never change old bills.
  5. One transaction per user action. A reading and its bill are committed together; if bill creation fails, the reading is rolled back too.
  6. Customer data isolation. Customer pages never take a customer id from the URL; they always use the logged-in user, and bill pages check ownership and return 403.
  7. Server-rendered pages instead of a JavaScript framework, to keep the stack simple for the team.
  8. Charts never mix units: charts that compare utilities use rupees; usage charts are drawn separately per utility (kWh, kL, SCM).
  9. No secrets in code: the secret key comes from config.py (git-ignored); a sample config.example.py is provided.
