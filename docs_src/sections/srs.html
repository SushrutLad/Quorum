Introduction

Purpose

This document specifies the requirements of the Energy & Utility Management System (EUMS). It is the agreed baseline between the development team and the course instructor, and it is the input to the design, implementation and testing phases of our Waterfall process.

Scope

EUMS is a web application for a utility office that supplies electricity, water and piped gas. It manages customers, connections and meters, records meter readings, generates slab-based bills automatically, accepts payments, and handles complaints and outages. It provides a staff portal (administrator and employees) and a customer self-service portal. Real payment gateways, smart meters, SMS/e-mail and mobile apps are out of scope.

Overall Description

Product perspective

EUMS is a new, self-contained system that replaces paper registers and spreadsheets. It is a three-tier web application (browser, Flask server, SQLite database).

Product functions

  • Manage users, customers, employees, connections and meters.
  • Record meter readings with validation; generate itemised slab-based bills.
  • Accept online and counter payments, including partial payments, and issue receipts.
  • Manage complaints and outages; notify customers.
  • Maintain tariffs; show dashboards and reports.

Operating environment

Server: any PC with Python 3.10+ and Flask (Windows, Linux or macOS). Client: any modern browser (Chrome, Edge, Firefox) on desktop or phone. Database: SQLite 3 file.

Design and implementation constraints

  • Free and open-source software only; must run on a student laptop without a database server.
  • Relational database with constraints, triggers and views (DBMS course requirement).
  • No passwords, API keys or real personal data in the source code or sample data.

Assumptions and dependencies

  • One connection per utility per customer; one active meter per connection; meters are cumulative.
  • Tariff depends only on the utility and the customer category (residential / commercial).
  • Bills are due 15 days after the bill date. Payment gateway is simulated.

External Interface Requirements

User interfaces

Web pages with a left navigation menu by role, a top bar with the user's name, cards for summaries, tables for lists and simple forms. Errors are shown as red messages at the top of the page; successes in green. Layout adapts to screens narrower than 800 px.

Software interfaces

Python Flask 3 web framework; SQLite 3 via Python's sqlite3 module; Chart.js 4 in the browser. A JSON endpoint GET /staff/api/meters/<id> returns the previous reading for the reading form.

Communication interfaces

HTTP between browser and server (HTTPS in a production deployment). Session cookie signed with a secret key.

Data Requirements

The system stores the following entities: users, customers, employees, utilities, tariff plans and slabs, connections, meters, meter readings, bills and bill items, payments, complaints, outages, notifications and an activity log. Key business rules on data:

  • BR-1: A meter reading must be ≥ the previous reading of the same meter, and later in date.
  • BR-2: Exactly one bill per meter reading; bill charges are fixed once issued.
  • BR-3: Total payments on a bill can never exceed the bill total. Status is unpaid, partial or paid.
  • BR-4: Customer email, customer code, connection number, meter number, bill number and receipt number are unique.
  • BR-5: A customer has at most one connection per utility.
